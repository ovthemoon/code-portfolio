# 계속 묻지 않고 바뀔 때만 알리고, 쉬는 동안은 깨우지 않는다

출처: 교실 실시간 그림 릴레이 게임(외주) (worker.js, 2026-09)

## 문제
참가자 화면이 상태를 주기적으로 다시 묻는 방식이라 요청 수가 접속자 수와 시간에 비례했다. 배포 당일 부하 테스트 중 Cloudflare 대시보드에 하루 요청 21만 6,166회가 찍혔고(본인 기록, 저장소에 근거 파일 없음), 원인은 화면이 0.8초마다 상태를 묻던 것이었다. 폴링 시절 코드는 현재 저장소에 없어 싣지 않았다.

## 해결
- WebSocket으로 서버가 상태를 밀어 준다. 소켓마다 마지막으로 보낸 revision을 저장해 두고, 바뀐 소켓에만 보낸다 (`planBroadcast`).
- 시간으로 일어나는 일(제한 시간 마감, 인증 기한, 끊긴 참가자 정리, 방 만료)은 알람 하나에 모은다. 후보 중 가장 이른 시각만 예약한다 (`nextAlarmAt`).
- Durable Object WebSocket Hibernation API를 쓴다. 객체가 메모리에서 내려가도 소켓별 상태(revision, 인증 여부)는 소켓 attachment에 남는다. ping은 플랫폼이 자동으로 응답해 객체를 깨우지 않는다.

## 코드
- `broadcast-plan.mjs`: 어느 소켓에 보낼지, 다음 알람을 언제로 할지 고르는 순수 함수
- `broadcast-plan.test.mjs`: 위 함수의 테스트
- `excerpt/relay-room.js`: 원본 Durable Object에서 소켓 수락, 방송, 알람 예약만 발췌

## 확인
```
cd js/ws-push-hibernation && node --test
```
`excerpt/`는 발췌만 있다 (Cloudflare Durable Object 런타임 전용이라 실행하지 않는다). "90초 동안 푸시 0회" 테스트는 원리를 모델로 확인하는 것이고, 실측은 아래 표다.

## 숫자와 조건
폴링을 바꾼 뒤 공개 서버에서 잰 값이다 (2026-09-29). 참가자 28명, 교사 1, 중계 1로 WebSocket 연결 30개, 7문제 완주. 참가자는 실제 휴대폰이 아니라 제품의 연결 코드를 실행한 자동 참가자다.

| 항목 | 값 |
|---|---|
| HTTP API 요청 | 35회 (정적 파일, 폰트, 이미지, QR 제외) |
| 게임 조작 명령 응답 | 중앙값 120ms, 95백분위 223ms |
| 참가 후 90초 대기 중 | HTTP 0회, 상태 푸시 0회 (ping, pong만 89회씩) |
| 오류, 재연결 | 0회 |

폴링 시절과 직접 비교한 수치는 없다. 측정 조건이 달라(전: 부하 테스트 중 하루치, 후: 28명 7문제) 절감 비율은 계산하지 않았다.

## 원본과 다른 점
- 알람과 방송 판정을 Durable Object 안의 인라인 계산에서 순수 함수로 뗐다. 입력은 소켓 attachment를 풀어 만든 값이다.
- 원본에서는 이 판정이 방송 반복문과 소켓 쓰기에 섞여 있어 Workers 런타임 없이는 테스트할 수 없었다. 여기서는 입력을 바꾸지 않고 새 값을 돌려준다.
- 알람 후보가 모두 무한대면 null을 돌려준다 (원본은 방 만료 시각이 항상 유한해 이 경우가 없다).
- 발췌에서 참가 주소 조립과 한국어 오류 문구를 뺐다. 연결 수 상한(`MAX_SOCKETS_PER_ROOM`)과 인증 기한(`AUTH_DEADLINE_MS`)은 예시값이다.
