# 동시 요청에서 "database is locked"가 나던 SQLite 트랜잭션

출처: OpenDesk (db.py, 2026-06)

## 문제
동료 여러 명과 동시에 대화하면 가끔 요금 예치(hold)가 "database is locked"로 실패했다. 예치는 잔액을 읽고 나서 줄이는 read-modify-write다. SQLite의 기본 트랜잭션은 읽기 스냅샷으로 시작해서 쓰기로 승격하는데, 그 사이 다른 연결이 커밋하면 스냅샷이 낡아 승격이 거절된다. 이 거절에는 `busy_timeout`이 적용되지 않아서, 타임아웃을 5초로 둬도 즉시 실패했다.

## 해결
- 트랜잭션을 처음부터 쓰기로 시작한다(`BEGIN IMMEDIATE`). 쓰기 자리를 얻으려는 쪽은 `busy_timeout` 동안 줄을 서고, 자리를 얻은 뒤에 읽으므로 스냅샷이 낡지 않는다.
- 극단적으로 몰려 타임아웃을 넘기면, 롤백한 뒤 지수 백오프와 지터로 트랜잭션을 통째로 다시 한다. 락이 첫 문장에서 잡혀 부분 커밋이 없으므로 다시 해도 안전하다. 횟수를 다 쓰면 마지막 예외를 올린다. 락 오류가 아닌 오류는 재시도하지 않는다.

## 코드
- `sqlite_write_lock.py`: 표준 `sqlite3`로 만든 같은 현상의 재현과 해법. `transaction`(IMMEDIATE와 DEFERRED 선택), 잔액 예치 `hold`, 동기 `retry_on_db_lock`.
- `test_sqlite_write_lock.py`: DEFERRED 승격 실패, IMMEDIATE 대기, 10개 스레드 동시 예치, 재시도.
- `excerpt/db_original.py`: 원본 발췌(SQLAlchemy async의 `begin` 이벤트와 비동기 재시도). SQLAlchemy가 필요해서 실행하지 않는다.

테스트가 겹침을 만드는 방법:
- DEFERRED 실패는 스레드 경합에 기대지 않고 결정적으로 만든다. 연결 A가 읽고, 연결 B가 쓰고 커밋하고, A가 쓰려 한다. 이때 A가 `busy_timeout`(3초)을 기다리지 않고 1초 안에 실패하는 것을 확인한다. WAL 모드 기준이다.
- IMMEDIATE는 한 연결이 쓰기 자리를 쥔 동안 다른 스레드가 `BEGIN IMMEDIATE`에서 대기하다가 통과하는 것을 보인다. 대기 시간이 0.15초 이상이고, 대기자가 쥔 쪽의 커밋을 읽고 이어서 쓴다.
- 10개 스레드가 장벽에서 동시에 출발하는 테스트는 결과 불변식만 본다. IMMEDIATE는 전부 성공하고 잔액과 예치 행 수가 맞는다. DEFERRED는 실패 여부를 단정하지 않고, 실패해도 조용한 덮어쓰기가 없고 성공한 개수만큼만 잔액이 줄었는지를 본다.
- 재시도 테스트는 실제 승격 실패를 첫 시도에서 만들고, 두 번째 시도가 새 스냅샷으로 성공하는 것을 확인한다.

## 확인
```
cd python && python3 -m pytest sqlite-begin-immediate
```

## 숫자와 조건
- 원본 테스트는 예치 10개 동시 요청이 모두 성공하고 잔액과 원장 합계가 맞는지 확인한다. 여기서도 10개 스레드, 건당 50, 시작 잔액 1000으로 같은 불변식을 본다.
- 재시도 4회, 기본 대기 50ms, `busy_timeout` 5초는 원본 코드의 값이다.
- 운영에서 발생한 횟수는 기록이 없다.

## 원본과 다른 점
- 원본은 SQLAlchemy async와 FastAPI 위에 있다. 여기서는 표준 `sqlite3`와 스레드로 같은 현상을 재현했고, 재시도 데코레이터는 동기 버전이다.
- 원본은 `session.rollback()`을 호출하고 여기서는 연결에 열려 있는 트랜잭션을 롤백한다.
- 데코레이터는 `sleep`과 `jitter`를 바꿔 끼울 수 있게 했고, 인자 없이 쓰는 형태도 지원한다.
- 테이블은 재현용 최소 스키마(지갑과 예치)다.
