# 결제 한 번에 크레딧이 두 번 들어가던 문제: 판정 전에 결제 세션 행을 잠근다

출처: OpenDesk (checkout_lock.py, router.py, reclaim.py, 2026-06, 2026-11)

## 문제
결제가 끝나면 결제사 알림, 결제 화면 콜백, 놓친 결제를 찾는 복구 작업 세 곳이 각자 확정을 시도한다. 셋이 쓰는 중복 방지 키가 서로 달라서 원장의 유니크 제약이 겹침을 막지 못했다. 남은 가드는 결제 세션의 상태뿐인데, 잠금 없이 읽으면 Postgres(READ COMMITTED)에서 두 확정자가 같은 pending을 동시에 보고 둘 다 적립했다. 웹훅이 유실돼 복구 작업이 먼저 확정한 뒤 결제사가 웹훅을 재전송해도 같은 일이 생겼다.

## 해결
- 확정자는 판정하기 전에 세션 행을 잠그고, 잠금 아래에서 최신 상태를 다시 읽는다. 이미 확정됐으면 건너뛴다. 잠금은 트랜잭션이 끝날 때까지 유지된다.
- 잠그는 순서는 늘 세션 행, 지갑 행이다. 반대 순서로 잡는 곳이 없어야 한다는 규칙을 코드에 적어 두었다.
- 같은 세션이 이미 올려 둔 행은 옛 상태를 돌려주므로 최신값으로 다시 읽는다(`populate_existing`).
- `refunded`도 확정으로 본다. 단 원래의 적립이 있을 때만이다. 환불이 결제보다 먼저 온 순서 역전은 늦게 온 결제가 적립해서 상쇄해야 하므로 막지 않는다.
- 관련 발췌로, 서버가 죽어 정산되지 못한 예치금을 TTL이 지난 것만 골라 이미 있는 멱등 환불로 돌려주는 `reclaim.py`를 함께 둔다. 환불 하나가 실패해도 나머지는 계속 처리한다.

## 코드
- `confirm_once.py`: 같은 아이디어를 `sqlite3`와 스레드로 줄여 실행하게 만든 것. 잠그고 읽는 확정자와 잠금 없는 확정자(고치기 전), 환불, `already_fulfilled`.
- `test_confirm_once.py`: 세 확정자가 동시에 같은 결제를 확정하는 테스트와 환불 순서 테스트.
- `excerpt/checkout_lock.py`: 세션 행 잠금(SQLAlchemy). 발췌만, 식별자는 일반 이름이다.
- `excerpt/already_fulfilled.py`: 이미 확정된 결제를 또 적립하지 않는 판정. 발췌만.
- `excerpt/reclaim.py`: 고아 예치금 회수. 발췌만.

테스트가 겹침을 만드는 방법:
- 잠금 없는 쪽은 세 스레드가 모두 상태를 읽은 뒤에야 쓰도록 장벽을 둔다. 세 확정자가 모두 pending을 보고 각자 다른 키로 적립해 세 번 들어간다.
- 잠금 있는 쪽은 쓰기 자리를 쥔 채 잠깐 멈춘다. 나머지 둘은 줄을 서 있다가 확정된 것을 보고 건너뛴다. 어느 확정자가 이기는지는 정해지지 않지만 적립은 정확히 한 번이다. 10번 반복한다.
- SQLite에는 행 잠금이 없어서 `BEGIN IMMEDIATE`가 그 역할을 한다. 원본도 SQLite에서는 같은 방식으로 쓰기를 직렬화한다.

## 확인
```
cd python && python3 -m pytest payment-confirm-row-lock
```
`excerpt/`는 SQLAlchemy와 원본 모델이 필요해서 실행하지 않는다.

## 숫자와 조건
- 테스트의 적립량(`UNITS`)은 예시값이다.
- 운영에서 겹침이 발생한 기록은 없다. 재현은 테스트에서 했다.

## 원본과 다른 점
- 원본은 Postgres의 `SELECT ... FOR UPDATE`와 SQLAlchemy async다. 여기서는 `sqlite3`, 스레드, `BEGIN IMMEDIATE`로 같은 현상을 재현했고 Postgres에서의 실제 겹침은 실행하지 않는다.
- 중복 방지 키 접두, 테이블과 컬럼 이름, 결제사 이름, 적립량은 일반 이름과 예시값으로 바꿨다. 확정자는 알림, 콜백, 복구 작업으로 부른다.
- 환불과 순서 역전 규칙은 원본 판정을 이 재현용 스키마에 맞춰 다시 쓴 것이다.
