# 토큰 상한에 잘린 모델 JSON에서 완성된 항목을 살린다

출처: OpenDesk (cron_interpret.py, 2026-06)

## 문제
반복 업무를 해석하는 모델 응답(질문 목록과 설정)이 서버의 출력 토큰 상한에 걸려 중간에서 끊겼다. `json.loads`가 실패해서 파싱 실패로 처리됐고, 앞쪽의 멀쩡한 질문까지 화면에 뜨지 않았다. 원인은 서버가 운영용 엔드포인트의 응답을 자체 상한으로 잘라 보내는 것이었다.

## 해결
- 서버 쪽 상한을 올렸다.
- 클라이언트도 서버를 못 올려도 동작하게 했다. 마지막으로 닫힌 컨테이너(`}` 또는 `]`)까지 자르고, 열려 있던 괄호를 역순으로 닫아 다시 파싱한다.
- 문자열 안의 괄호와 이스케이프된 따옴표는 문자열 경계를 추적해서 무시한다.
- 닫힌 컨테이너가 하나도 없으면 복구하지 않고 실패로 둔다. 호출자가 폴백을 탄다.
- 첫 파싱이 성공하면 복구를 건드리지 않는다. 복구는 실패했을 때 한 번만 시도한다.

한계: 절단점이 안쪽 배열의 닫힘이면 그 항목은 살지만 배열 뒤의 필드는 잃는다. 호출자가 빠진 필드에 기본값을 두어야 한다. 테스트로 고정했다.

## 코드
- `truncated_json.py`: `repair_truncated_json`(원본 `_repair_truncated_json`)과 코드 펜스를 걷고 복구까지 이어 주는 `parse_model_json`.
- `test_truncated_json.py`: 문자열 중간과 키 뒤에서 끊긴 경우, 괄호 순서, 문자열 안의 괄호, 복구 불가, 쓰레기 입력, 모든 절단 위치 훑기.

## 확인
```
cd python && python3 -m pytest truncated-json-repair
```

## 숫자와 조건
서버의 운영용 출력 상한을 300에서 1024로 올렸다(2026-06 커밋 메시지 기준). 발생 빈도는 측정하지 않았다.

## 원본과 다른 점
- 원본의 `parse_interpret`은 복구 뒤에 질문과 설정 정규화, 허용 값 필터를 이어 한다. 여기서는 JSON을 꺼내는 부분만 `parse_model_json`으로 떼어 냈다.
- 테스트는 원본의 질문 목록 예시를 영어 예시로 바꾸고, 모든 절단 위치를 훑는 테스트와 한계 테스트를 더했다.
